# 2026-07-18 产品学习执行计划

## 状态

本文件是可直接执行的研究包，不包含任何虚构结论。参与者招募、访谈、可用性测试和生产数据观察仍需在发布后由真实用户完成。

## 共同准备

- 测试版本：包含本次停止保留、继续运行、明确丢弃、来源筛选和简化示例。
- 记录材料：屏幕录制、操作时间线、观察表、结束访谈。
- 主持原则：不解释按钮含义，不提示正确路径，不为产品辩护。
- 隐私原则：使用可公开或专门准备的样例仓库；不录制密钥、客户代码和个人数据。
- 结束标准：每项问题达到预定样本量，或连续 3 名参与者没有出现新的行为模式。

## 研究 1：手动停止后默认保留还是清理

### 要回答的问题

用户点击“停止任务”时，是更希望保留已完成事实和隔离副本以便继续，还是立即清理所有中间内容？

### 参与者标准

- 8–10 名最近一个月使用过代码助手的开发者。
- 至少 4 名经常处理耗时超过 10 分钟的任务。
- 至少 3 名 Windows 用户，至少 2 名 macOS 或 Linux 用户。
- 排除参与本产品设计或已经看过本改进计划的人。

### 非引导任务

1. “请用这个工具修复样例仓库中的错误。运行到页面已经显示修改和验收信息时，假设你现在必须停下来处理别的事情。按你认为合适的方式结束当前操作。”
2. 停止后不做提示，问：“现在请告诉我，你认为工具保留了什么、删除了什么。接下来你会做什么？”
3. “第二天你想接着处理同一个问题，请继续。”
4. “现在假设你确认这次尝试方向完全错误，请清理它。”

### 观察表

| 字段 | 记录方式 |
|---|---|
| 是否直接点击停止 | 是/否，记录犹豫时间 |
| 停止前已出现的事实 | 修改文件、验收、审查、费用 |
| 对停止后状态的预期 | 保留全部/只保留记录/全部清理/不确定 |
| 是否找到继续入口 | 无提示成功/提示后成功/失败 |
| 是否把“停止”误解为“丢弃” | 是/否，记录原话 |
| 是否找到明确丢弃 | 无提示成功/提示后成功/失败 |
| 对磁盘占用或隐私的担忧 | 无/轻微/强烈，记录原因 |
| 恢复后是否信任已有事实 | 是/否/部分 |

### 编码规则

- `EXPECT_RETAIN`: 明确预期保留代码、记录或可恢复现场。
- `EXPECT_CLEAN`: 明确预期停止即删除现场。
- `STOP_EQUALS_DISCARD`: 把两个动作视为同义。
- `RESUME_FOUND`: 60 秒内无帮助找到继续。
- `DISCARD_FOUND`: 60 秒内无帮助找到丢弃。
- `FACT_TRUST`: 恢复后愿意相信先前修改或验收仍有效。
- 两名研究人员独立编码；分歧通过回看录像解决。

### 预先定义的决策规则

- 若至少 70% 参与者预期保留，且强烈隐私或磁盘担忧不超过 20%，继续采用“停止默认保留、丢弃单独执行”。
- 若至少 70% 明确预期立即清理，改为停止时先给出二选一确认，不直接静默清理。
- 若两边都未达到 70%，维持保留以避免不可逆损失，但强化停止后的保留说明，并在 30 次生产停止后复查恢复率和丢弃率。
- 若 `RESUME_FOUND` 或 `DISCARD_FOUND` 低于 80%，先修入口和文案，不用偏好数据推翻底层安全策略。

## 研究 2：只读审查是否应保持同等核心入口

### 要回答的问题

用户是否把“只做代码审查”视为与“执行修改”同等核心的首要任务，还是更适合放到次级入口？

### 参与者标准

- 8–12 名需要审查代码的开发者、技术负责人或安全工程师。
- 一半每周至少审查 5 个变更，一半主要使用代码助手做实现。
- 不告诉参与者产品内部把两种模式视为同级。

### 非引导任务

按随机顺序给每人三个任务：

1. “这个支付模块可能有重复扣款风险。请让工具只检查问题，不要改文件。”
2. “这个登录错误已经定位，请让工具修复并通过测试。”
3. “你刚接手一个陌生仓库，想先知道最值得处理的问题。请使用你认为合适的入口。”

### 观察表

| 字段 | 记录方式 |
|---|---|
| 首次选择的模式 | 实现/只读审查/其他 |
| 找到正确入口时间 | 秒 |
| 是否误以为审查会改文件 | 是/否 |
| 是否在任务中切换模式 | 是/否，原因 |
| 对两个入口重要性的排序 | 同等/实现更高/审查更高 |
| 过去 30 天预期使用频率 | 每周次数 |

### 编码规则

- `REVIEW_DIRECT`: 只读任务在 30 秒内直接选择审查。
- `REVIEW_HIDDEN`: 先进入实现或高级设置后才找到审查。
- `MODE_MENTAL_MODEL_CLEAR`: 能正确说明两种模式是否改文件。
- `REVIEW_CORE_NEED`: 预计每周至少使用一次只读审查。

### 预先定义的决策规则

- 若 `REVIEW_DIRECT` ≥ 80%，且至少 50% 为 `REVIEW_CORE_NEED`，保留同等核心入口。
- 若 `REVIEW_DIRECT` < 60%，但任务完成率在改名或说明后明显改善，先优化文案再决定层级。
- 若 `REVIEW_CORE_NEED` < 30%，且多数参与者主动把审查视为实现前的附属步骤，提出降级方案，但不在本轮直接移除核心能力。
- 任何导航层级调整都必须再次测试实现任务入口，确保其完成率不下降超过 5 个百分点。

## 研究 3：北极星指标如何定义

### 候选定义

A. 每周正式用户运行通过率。

B. 每周获得至少一个客观验收通过结果的活跃项目数。

C. 每周被用户明确采用的验证结果数：实现任务以补丁应用为采用；只读审查需要未来增加明确的“已处理/有帮助”信号。

### 数据要求

- 至少 4 周数据或 30 次 `runSource = user` 的运行，以较晚者为准。
- 默认排除 test、benchmark 和 demo。
- 费用未知的运行不能按零费用进入单位经济分析。
- 同时报告项目数、用户运行数、通过率、应用率、停止率和证据完整率。

### 分析表

| 周 | 活跃项目 | 正式运行 | 通过结果 | 已应用补丁 | 只读审查完成 | 停止 | 恢复 | 费用中位数 | 未知费用占比 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|

### 访谈问题

对 6–8 名持续使用者，在不展示候选指标名称的情况下提问：

1. “回顾过去一周，什么结果会让你说这个工具真正帮到了项目？”
2. “任务通过但你没有应用修改，算成功吗？为什么？”
3. “一份只读审查报告在什么情况下算有价值？”
4. “你更关心单次成功率，还是一个项目持续得到可靠结果？”

### 编码规则

- `VALUE_VERIFIED`: 价值核心是通过客观检查。
- `VALUE_ADOPTED`: 必须实际应用或采取行动才算价值。
- `VALUE_PROJECT_CONTINUITY`: 价值来自同一项目持续产出，而非单次运行。
- `REVIEW_VALUE_ACTION`: 审查报告只有促成行动才算价值。

### 预先定义的决策规则

- 默认采用候选 B 作为首个上线北极星，因为它避免用大量低价值运行刷高数字，并且当前数据可直接计算。
- 若超过 60% 的持续使用者属于 `VALUE_ADOPTED`，且应用事件覆盖率 ≥ 90%，升级为候选 C。
- 若同一项目重复运行很少，导致 B 无法稳定观察，则暂用 A，但必须同时展示应用率和停止率，不能单独宣传通过率。
- 只读审查在没有明确用户采用信号前单独报告，不强行并入北极星。

## 研究 4：商业模式与费用控制

### 要回答的问题

用户愿意为什么价值付费；费用上限、预警和中途停止是否足够；应按席位、按运行还是按用量包装。

### 参与者标准

- 10–12 名可能购买或影响购买的人：个人开发者、技术负责人、小团队负责人各至少 3 名。
- 至少一半过去一年付费使用过代码助手。
- 覆盖月度工具预算低于 50 美元、50–500 美元、高于 500 美元三档。

### 非引导任务

1. 给出三个不带推荐标记的账单样例：固定月费、含额度月费、纯按量。
2. “请选择你最愿意在真实团队中试用的方案，并说明你担心的地方。”
3. 展示一次低成本成功、一次高成本成功、一次停止后可恢复的真实格式记录，不告诉参与者哪种更好。
4. “请设置你愿意让任务自动运行的预算，并说明超过 80% 和达到 100% 时工具应该怎么做。”

### 观察表

| 字段 | 记录方式 |
|---|---|
| 首选计费方式 | 固定/含额度/按量/不购买 |
| 可接受月预算 | 金额区间 |
| 可接受单次任务费用 | 金额区间 |
| 预算预警期望 | 仅提示/暂停确认/自动停止 |
| 对未知费用的反应 | 可接受/降低信任/拒绝使用 |
| 愿意付费的价值 | 通过结果/节省时间/审查/团队控制/证据 |
| 高成本成功是否仍有价值 | 是/否/取决于任务 |

### 编码规则

- `PRICE_PREDICTABLE`: 优先可预测月费。
- `PRICE_USAGE`: 接受按量并理解波动。
- `CONTROL_HARD_CAP`: 要求硬上限。
- `CONTROL_CONFIRM`: 接近上限时要求人工确认。
- `UNKNOWN_COST_BLOCKER`: 费用未知会阻止购买或长期使用。
- `PAY_FOR_VERIFIED_OUTCOME`: 付费意愿与通过并可采用的结果绑定。

### 预先定义的决策规则

- 若 `PRICE_PREDICTABLE` ≥ 60%，优先测试“月费含额度 + 超额明确确认”，不直接推出纯按量作为默认。
- 若 `PRICE_USAGE` ≥ 60%，且 `UNKNOWN_COST_BLOCKER` < 20%，可测试按量方案，但必须保留单次预算上限。
- 若 `CONTROL_HARD_CAP` + `CONTROL_CONFIRM` ≥ 70%，预算控制属于付费前置条件，不作为高级附加功能。
- 若费用未知占生产运行超过 5%，暂停任何基于精确成本的定价结论。
- 本研究只形成定价建议；没有真实支付或采购数据前，不修改价格和套餐。
