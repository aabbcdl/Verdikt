# 产品测量矩阵

## 目的

这份矩阵只记录会支持真实产品决策的数据。当前记录保存在每次运行目录的 `events.jsonl`、`summary.json` 和 `state.json` 中；正式任务统计只纳入未归档且 `runSource = user` 的运行，示例、测试、benchmark、未知来源和已归档记录仍会保留并可单独查看。

## 数据边界

- 允许：运行来源、阶段、轮次、是否通过、停止原因、是否可继续、费用完整性、费用、耗时、文件数量、应用或丢弃状态。
- 不进入汇总分析：任务目标原文、项目绝对路径、代码、补丁内容、日志正文、命令输出、密钥、个人信息。
- 本地证据文件仍可保留完整内容，但任何后续导出只能使用上面的允许字段。
- 老记录没有来源时标为 `unknown`；只有能明确识别的旧测试记录才标为 `test`。

## 事件与决策

| 事件或记录 | 触发时机 | 必要字段 | 支持的决策 | 去重规则 |
|---|---|---|---|---|
| `run_started` | 新运行目录创建并写入任务后 | `runId`、`taskId`、`runSource`、时间 | 示例是否被启动；不同来源的使用量 | 每个 `runId` 只计第一条 |
| `workspace_ready` | 隔离副本或直接工作区准备完成 | 模式、是否恢复、准备耗时 | 首次启动是否被环境准备拖慢 | 每次启动或恢复各计一次 |
| `plan_started` / `plan_completed` | 规划开始与结束 | `runId`、费用状态、费用 | 自动规划是否带来额外时间和费用 | 同一运行同一规划阶段只配对一次 |
| `iteration_started` | 一轮正式开始 | 轮次、阶段、是否从部分进度恢复 | 恢复后是否重复工作 | `runId + iteration` 唯一；恢复可用 `resumedPartial` 区分 |
| `executor_started` / `executor_completed` | 执行阶段开始与结束 | 轮次、阶段、耗时、费用状态 | 执行耗时、费用和失败位置 | `runId + iteration + phase` 只取首个开始和最后完成 |
| `patch_ready` | 当前轮修改事实已捕获 | 轮次、文件数、增删行数 | 停止前是否已经产生可保留成果 | `runId + iteration` 只计最后一条 |
| `judges_started` / `judges_completed` | 验收命令开始与结束 | 轮次、通过状态、检查数量 | 验收阶段耗时和通过率 | `runId + iteration + phase` 配对 |
| `verifier_started` / `verifier_completed` | 审查开始与结束 | 轮次、是否完成、问题数、费用状态 | 审查阶段的停滞和额外成本 | `runId + iteration + phase` 配对 |
| `phase_stalled` | 某阶段超过软停滞阈值 | 阶段、静默时长、总时长、轮次 | 哪个阶段最常让用户等待或停止 | 同一阶段连续无活动只计一次；活动恢复后可重新计 |
| `run_cancel_requested` | 用户点击停止 | 当前阶段、来源 | 用户在哪个阶段主动停止 | 每次运行的每次停止请求计一次 |
| `run_cancelled` | 停止完成且状态已保存 | 原因、轮数、费用、耗时、可继续 | 停止后保留策略是否可用 | 每个停止结果计一次 |
| `run_resumed` | 用户继续已保留运行 | 下一轮位置、来源 | 停止后的继续率 | 每次恢复计一次 |
| `run_completed` | 运行形成最终结果 | 结束原因、轮数、费用、耗时 | 示例完成率、正式任务通过率、成本和耗时 | 每次最终结果计一次 |
| `patch_applied` / `patch_discarded` | 用户明确应用或丢弃 | `runId`、状态 | 通过结果是否被采用；保留是否造成积压 | 一个运行只接受第一个终态 |
| `summary.json` | 停止或结束时 | 来源、结果、部分轮次、是否可继续、费用、耗时 | 历史和统计的最终事实 | 以最新原子写入版本为准 |
| `state.json` | 可恢复检查点写入 | 当前阶段、部分轮次、下一轮、工作区 | 是否真的可以安全继续 | 与同目录 summary 合并读取，不覆盖 summary 中已完成事实 |

## 指标定义

### 1. 示例完成率

- 分母：`runSource = demo` 的唯一 `run_started`。
- 分子：同一运行出现 `run_completed`，结束原因为 `passed` 或 `review_completed`。
- 同时报告：停止率、恢复率、费用中位数、耗时中位数、费用未知占比。
- 不把测试或 benchmark 放进示例指标。

### 2. 停止恢复率

- 分母：`run_cancelled` 且 `resumable = true` 的运行。
- 分子：这些运行后续出现 `run_resumed`。
- 辅助指标：恢复后最终通过率、停止到恢复的时间、明确丢弃率。

### 3. 阶段停滞率

- 分母：进入某阶段的唯一运行轮次。
- 分子：该阶段出现 `phase_stalled` 的唯一运行轮次。
- 分阶段报告 planning、reviewing、executor、judges、verifier、finalizing，不合并成一个模糊总数。

### 4. 暂定北极星指标

**每周获得至少一个“客观验收通过结果”的活跃项目数。**

- 项目按本地匿名项目标识聚合，分析时不导出绝对路径。
- 实现任务的有效结果：`runSource = user`、结束原因为 `passed`。
- 只读审查是否纳入同一北极星，等待研究决策；在决策前单独报告 `review_completed`。
- 守护指标：应用率、待应用积压、费用未知占比、每个通过结果的费用中位数、停止率、完整证据率。
- 这只是上线测量口径，不代表已经证明它与留存或收入相关。

## 上线后读取方式

1. 按 `runId` 合并 `events.jsonl`、`summary.json`、`state.json`。
2. 先按 `runSource` 分层；正式任务统计只使用未归档的 `runSource = user`，示例指标只使用 `runSource = demo`，其他来源不混入两者。
3. 同时存在 summary 和 state 时，summary 提供已完成事实，state 提供是否可继续和当前部分进度。
4. 费用状态不是 `complete` 时，不把缺失费用当作零；单独报告未知占比。
5. 周报必须同时给出样本量，样本不足 30 次正式用户运行时只展示原始数量，不宣称趋势。

## 发布后检查节奏

- 发布后第 1 天：确认事件能配对、没有重复、停止后 summary 与 state 同时可读。
- 第 1 周：检查示例启动、完成、停止和费用分布；只做故障判断，不做长期产品结论。
- 满 30 次正式用户运行或 4 周后：按研究计划执行第一次决策复盘。
